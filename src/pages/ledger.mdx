The ledger is a folder tree in a public repository. Every prediction the models make is a set of files in it, committed to a protected branch by a scheduled workflow and never edited afterwards. This page lists what's there and explains how to read an entry. The site computes nothing the repository doesn't already state: it only counts files and copies figures.

## What one entry is

Each predicted event has its own folder, whose path names the court, the docket, and the event:

```
data/cases/<court>/<docket>/events/<event>/
  event.yaml                          what is being predicted: stage and decision target
  outcome.json                        what the Court did, once it has
  predictions/<model>/<run>/
    prediction.json                   the probability, the call, and at merits the judgment and votes
    reasoning.md                      why this number
    predicted_reasoning.md            what the Court will do, and on what grounds
    retrieval.md                      what the model consulted beyond the materials it was given
  evaluations/<evaluator>/<model>/<run>/
    evaluation.json, evaluation.md    one evaluator's grading of one prediction
```

The `<run>` folder is named with a UTC timestamp, so a rerun writes a new folder beside the old one instead of overwriting it. Inside `prediction.json`, the `process_version` block records which frozen process produced the prediction and when the system stamped it. That stamp is written by the machine that ran the model, not by the model itself.

## How to check that a prediction preceded an outcome

Pick any resolved row in the table below. Its `outcome.json` records when the event resolved; for a cert petition, that's the date of the order list. Then:

1. Open the prediction's folder on GitHub and note the `stamped_at` time in `prediction.json`.
2. Find the commit that added the file: use the GitHub history for `prediction.json`, or from a clone run `git log --diff-filter=A --format='%H %cI' -- <path>`. The commit reached `main` through a pull request, and the merge time is on the pull request's page.
3. Open the workflow run linked from that pull request. Its start and end times show the window in which the model was actually running.
4. Compare all three times with the order list on supremecourt.gov for the conference in question.

None of these three clocks (the system's stamp, the pull request merge, and the workflow run) can be set by the model. All three should fall before the outcome, and they should agree with each other to within the length of the run. If they don't, please [open an issue](https://github.com/ModelMirrorAI/fedcourtsai/issues).

It's worth being precise about what this proves. It shows that a specific prediction was public, in this exact form, before the Court acted. It doesn't show that the model had no way of knowing the outcome: a petition already granted quietly, a commentator who guessed right, an order the model found by searching. Those are leakage questions. After the event resolves, a grader reads each prediction's research record looking for them. A prediction found to have leaned on the outcome is excluded and marked, not deleted.

## Frozen and shakedown

Predictions made before the process was frozen on {ledger.frozen_process.since ? ledger.frozen_process.since.slice(0, 10) : "the freeze date"} stay on the ledger with their timestamps. They were made while the prompts and settings were still changing, so nothing about them was pre-registered and no reported figure includes them. The table marks them as shakedown. Only frozen-scope events count toward the results.
